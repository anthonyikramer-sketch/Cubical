I want to consolidate and finalize the current widget interaction system.

The existing implementation is close, so DO NOT redesign the application or replace working systems unnecessarily.

Preserve all existing functionality that is already working.

This prompt should be treated as the current source of truth for widget behavior.

==================================================
1. GLOBAL RULE: WIDGETS ARE ALWAYS MOVABLE
==================================================

Widgets must be draggable during NORMAL Cubical use.

The user must NOT need to enter Edit Widgets mode to move widgets.

This applies to:

- Home
- Store
- Library
- Breakroom
- nested tool views belonging to Store/Library/Breakroom

NORMAL MODE:

- widgets can be dragged
- widgets can be moved around Home
- portable widgets can be transferred between valid tabs
- transported widgets can be reordered

EDIT WIDGETS MODE:

Widgets remain draggable exactly as they are during normal use.

Edit Widgets exists for management functionality such as:

- Add Widget
- Remove Widget / X
- resize controls where appropriate

Edit Widgets does NOT enable dragging.

Dragging is an always-on widget behavior.

==================================================
2. VALID WIDGET DESTINATIONS
==================================================

Portable widgets may exist in and move directly between:

- Home
- Store
- Library
- Breakroom

They may NOT be transported into:

- Profile
- Settings

A widget does NOT need to return Home before being transferred somewhere else.

Examples:

Home -> Library
Library -> Store
Store -> Breakroom
Breakroom -> Library
Library -> Home

All should work directly.

==================================================
3. CROSS-TAB DRAGGING FROM ANY LOCATION
==================================================

A portable widget should be draggable to another valid main tab regardless of where it currently exists.

This includes widgets currently located:

- freely on Home
- in Store's transported-widget area
- in Library's transported-widget area
- in Breakroom's transported-widget area
- inside a nested tool view belonging to one of those tabs

During cross-tab dragging:

- lift the widget visually out of its current layout
- attach it naturally to the cursor
- render it above normal page content
- render it ABOVE the sidebar
- preserve full widget visibility
- allow valid sidebar destinations underneath it to remain detectable

Use the same shared drag system regardless of origin.

==================================================
4. DRAGGED WIDGETS MUST RENDER ABOVE SIDEBAR
==================================================

This is important.

During active drag:

DRAGGED WIDGET
must visually render ABOVE
SIDEBAR

The entire widget must remain visible as it crosses the sidebar.

Do not allow the sidebar to cover or clip the widget.

Do not assume z-index alone is sufficient.

Inspect:

- stacking contexts
- transformed ancestors
- overflow clipping
- portal structure
- drag overlays

If necessary, render the active dragged widget through a top-level drag overlay / React portal near the application root/body.

The visual result must be:

widget floating above sidebar

while sidebar destinations underneath remain detectable.

==================================================
5. REMEMBER EXACT DRAG ORIGIN
==================================================

Whenever dragging begins, record the widget's exact origin.

For Home remember:

- X
- Y
- width
- height
- widget state

For transported tabs remember:

- tab
- row
- order/index
- transported size/state

Do NOT permanently update the saved location until a valid drop succeeds.

==================================================
6. VALID DROP
==================================================

If the widget is released over a valid main-tab destination:

- transfer the SAME widget
- do not duplicate it
- update its current section
- preserve its data/state
- preserve skin decorations
- preserve its canonical Home position and Home dimensions

Valid destinations:

- Home
- Store
- Library
- Breakroom

==================================================
7. SUCCESSFUL TRANSFER MUST NOT NAVIGATE THE USER
==================================================

When I send a widget to another tab:

MOVE THE WIDGET.

DO NOT MOVE ME.

Example:

I am on Home.

I drag Notepad onto Library.

Result:

- Notepad transfers to Library
- Notepad disappears from Home
- Library now contains Notepad
- I REMAIN ON HOME

When I later manually open Library, Notepad is already there.

Another example:

I am in Library.

I drag Calculator onto Breakroom.

Result:

- Calculator transfers to Breakroom
- Calculator disappears from Library
- I REMAIN IN LIBRARY

Do NOT automatically navigate to Breakroom.

This applies to ALL successful widget transfers.

==================================================
8. SUBTLE TRANSFER FEEDBACK
==================================================

Because the user remains on the current page after transferring a widget, provide subtle confirmation.

For example:

"Notepad moved to Library"

Keep this:

- brief
- non-blocking
- visually restrained
- consistent with Cubical styling

Do not use a modal.

==================================================
9. INVALID DROP = RETURN TO EXACT ORIGIN
==================================================

If a widget is released somewhere invalid:

- do not transfer it
- do not save the invalid location
- do not navigate
- return it to EXACTLY where the drag began

For Home:

restore exact original X/Y and size.

For Store/Library/Breakroom:

restore exact original row/order position.

Invalid destinations include:

- Profile
- Settings
- empty sidebar regions
- unsupported page areas
- outside the application
- any other invalid destination

Use a quick smooth return if desired.

Do not use an exaggerated bounce.

==================================================
10. HOME MOVEMENT VS INVALID CROSS-TAB DROP
==================================================

Preserve free movement on Home.

If the user is simply repositioning a Home widget and releases near an unusable boundary:

Cubical may gently keep it within usable workspace.

However, if the user is clearly attempting a cross-tab transfer and releases over an invalid destination:

Return the widget to its drag origin.

Do not confuse normal Home positioning with cross-tab transfer behavior.

==================================================
11. FREE MOVEMENT + SOFT SNAP
==================================================

KEEP the current free movement system.

I like that widgets can move freely without being locked to a rigid grid.

Also KEEP the subtle soft-snap/alignment assistance.

However, the current soft snap has too much RUBBER-BANDING.

Fix this.

The snap should behave like a gentle magnetic alignment assist.

It should:

- activate only when reasonably close to a useful alignment point
- provide subtle positional assistance
- release immediately when the cursor moves away
- never fight against intentional cursor movement
- never oscillate between snapped and unsnapped positions
- never repeatedly pull the widget backward
- never visibly tug the widget toward an old snap target
- never create a bungee-cord/rubber-band feeling

THE USER'S CURSOR MUST REMAIN AUTHORITATIVE AT ALL TIMES.

Think:

gentle magnetic guide

NOT:

spring-loaded attachment.

==================================================
12. SNAP HYSTERESIS / STABILITY
==================================================

Prevent rapid snap/un-snap oscillation.

If necessary, use separate thresholds:

- a small threshold to ENTER a snap
- a slightly larger threshold to LEAVE the snap

But the release distance must remain small enough that the user never feels trapped.

Do not continuously recalculate competing snap targets in a way that causes jitter.

Once the cursor clearly moves away from a snap target:

release it immediately and resume completely free movement.

==================================================
13. CLICK VS DRAG MUST BE DISTINGUISHED
==================================================

Dragging a widget must NOT activate that widget when released.

There is currently/previously an issue where dragging Calendar can also cause Calendar to open afterward.

Fix this at the SHARED widget interaction level.

Use a small drag threshold.

Conceptually:

pointer down
-> record position

little/no movement
-> pointer up
-> CLICK

movement exceeds approximately 4–6 CSS pixels
-> interaction becomes DRAG

pointer up after drag
-> DROP ONLY

Once an interaction becomes a drag:

SUPPRESS click activation on release.
